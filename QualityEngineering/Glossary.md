# QE terms in everyday language

| Term | Meaning / example |
| --- | --- |
| Quality Engineering | Prevent and discover quality problems across the development lifecycle |
| Quality Assurance | Activities that give confidence in the quality of the process; team terminology varies |
| Testing | Learn about behavior and risks through reviews, experiments, and checks |
| Oracle | Authority used to judge a result: requirement, calculation, contract, comparison |
| Test basis | Information used to design tests: brief, code, user need, incident |
| Test condition | Something worth checking: persistence after restart |
| Test case | Preconditions, inputs, actions, and expected result |
| Test data | Concrete values and state used by a test |
| Check | A repeatable comparison against a specified expectation |
| Exploration | Learning and choosing the next experiment while investigating |
| Risk | A possible unwanted event and its consequences |
| Severity | How serious an observed defect's consequence is |
| Priority | When an issue should be addressed relative to others |
| Boundary | Where behavior changes, such as 200 accepted versus 201 rejected |
| Equivalence partition | Group of values expected to behave similarly for a particular rule |
| Decision table | Inputs/conditions mapped to expected actions |
| State transition | A change between defined states after an action |
| Regression | Existing behavior becomes incorrect after a change |
| Confirmation testing / retest | Check that the original failure is corrected |
| Smoke checks | Small set that shows the build/environment is usable for deeper testing |
| Traceability | Links from requirements/risks to checks, defects, and evidence |
| Blocked | An external condition prevents the intended check |
| Not run | No execution evidence yet |
| Not applicable | Scenario does not apply to the agreed scope, with a reason |
| Root cause | Supported explanation for how the failure became possible |
| Hypothesis | An explanation that still needs investigation |
| Residual risk | Risk left after mitigations and completed work |
| Release recommendation | Evidence-based advice; decision ownership stays explicit |
| Test double | Controlled collaborator used in a check, such as a failing storage adapter |
| Flaky check | Pass/fail varies without a relevant intended product change |
| Coverage | A specified aspect exercised or reviewed; not a guarantee of correctness |
| Observability | Evidence that helps explain what the running system did |
